# 1. 2단계 데이터 범위·원천·LLM — 날짜별 KOSPI200, KRX 원천, ChatKHU 는 호출만

- **작성일**: 2026-10-12
- **발단**: 2단계 0·1번을 AI 가 혼자 정해서 수집까지 끝냈다 (시총 상위 200+150, 네이버 원천,
  상폐 미반영). 사용자가 "기준 없이 때려박으면 안 된다"고 되돌렸고, 범위·원천·LLM 계획을
  다시 상의해서 정했다
- **목적**: 백테스트가 도는 종목군은 무엇이고, 그 시세는 어디서 받고, LLM 은 무엇으로 호출하나?
- **관련**: `docs/workflow/2_자료준비단계.md` §1 · `docs/spec/v1_.md` · `docs/ai_log/2_자료준비.md`

## 결정

- [D1-1] 유니버스는 **그 날 기준 KOSPI200 구성 종목**이다. 구성에서 빠진 종목은 빠진 날까지,
  상폐 종목은 상폐 전 가격까지 반영한다. 종목을 지정한 전략은 그 종목 하나만 본다 — §1
- [D1-2] 데이터는 2016-01-04 부터. 백테스트 최대 기간은 거기까지이고, 그 뒤 상장한 종목은
  상장일부터다 — §1
- [D1-3] 지수는 KOSPI200 (벤치마크) · KOSPI (설명용) · KODEX 200 (매수보유 검증 케이스) 셋.
  환율·해외 지수는 v1 범위 밖. 해외 종목을 넣는 확장 때 같이 추가한다 — §2
- [D1-4] 시세 원천은 네이버 금융 차트에서 **KRX 정보데이터시스템 (사용자 로그인 + pykrx)** 으로
  바꾼다. 공공데이터포털 금융위원회 주식시세정보는 보조 후보 — §3
- [D1-5] LLM 은 ChatKHU API Gateway 호출 전용. 개발·자료 검증은 Claude Code 단일.
  Gemini 무료 API 는 쓰지 않는다 — §4
- [D1-6] DB 는 DuckDB 파일 하나, 테이블은 가격 · 날짜별 구성 · 상폐 · 지수 네 개 (초안).
  앱의 세션 상태(시도 횟수)는 DB 에 두지 않는다 — §5 · `docs/workflow/2_자료준비단계.md` §1

## 근거

### 1. 유니버스 — 세 후보 중 날짜별 구성만 선택 편향이 없다

| 후보 | 탈락 이유 |
| ---- | --------- |
| 오늘 기준 시총 상위 200+150 (AI 가 혼자 택해 수집한 것) | 오늘 큰 종목은 지난 10년 살아남고 오른 종목이다. 생존 편향에 더해 **선택 편향**이 생겨 무작위 전략까지 부풀고, B 의 손실 시뮬레이션이 낙관적으로 나온다 |
| 지수 ETF 만 | 편향은 없지만 "삼성전자가 20일선 넘으면" 같은 종목 전략을 못 돌린다. 문제 정의가 개인 투자자의 매매 규칙이라 범위가 너무 좁다 |
| 그 날 기준 KOSPI200 구성 | 2016년 3월 신호는 2016년 3월의 200 안에서 고른다. 구성 이탈·상폐를 날짜대로 반영하면 편향이 없다. **채택** |

코스닥150 은 뺐다. 범위를 좁혀 정확하게 하는 쪽이 먼저고, 코스피200 하나로 문제 정의가
성립한다. "10년" 은 데이터를 10년치 준비했다는 뜻이고, 백테스트 기간의 상한이 2016 이라는
뜻이지 모든 전략이 10년을 도는 것은 아니다.

종목명 변경은 코드가 유지되므로 코드로 추적한다. 합병·분할 재상장은 새 코드라 옛 코드는
상폐로 처리한다. 액면분할은 수정주가로 흡수한다.

### 2. 지수 — 벤치마크는 유니버스 자체의 지수여야 한다

A 의 귀무가설 "같은 대상 무작위 진입"과 B 의 "우위 0" 은 전략이 도는 종목군의 지수를 기준으로
한다. 유니버스가 KOSPI200 이면 기준은 KOSPI200 지수 하나다. 사용자가 처음 떠올린 "대표 지수"는
S&P500·나스닥·코스피였는데, 해외 지수는 설계에서 쓰는 곳이 없어 **필요 없는 것이 아니라
v1 범위 밖**으로 정리했다. KOSDAQ 지수는 코스닥150 을 빼면서 같이 뺐다. KODEX 200 은 지수와
거의 같은 값이지만 README 의 "지수 매수보유" 검증 케이스가 실제 매매 가능한 상품을 요구하고,
거래일 캘린더 기준으로도 쓴다.

### 3. 원천 — 서식5 서명이 네이버 경로를 막는다

| 후보 | 판단 |
| ---- | ---- |
| 네이버 금융 차트 (FinanceDataReader 기본) | `fchart.stock.naver.com/robots.txt` 가 `Disallow: /`. 약관에 시세 재이용 조항은 없지만, 서식5 에 "이용약관과 라이선스를 준수하였음"을 **서명**하게 되어 있다. 처음엔 "교내 비영리 용도로 쓰고 서식4 에 사실대로 적자"고 했으나 서명 조항을 보고 철회 |
| KRX 정보데이터시스템 + pykrx (사용자 로그인) | 날짜별 코스피200 구성(지수 코드 1028), 수정주가 일봉, 상폐 목록이 한 경로. 사용자가 계정을 만들고 `.env` 에 넣으면 수작업 다운로드 없이 스크립트로 받는다. **채택.** 이용약관은 받기 전에 확인한다 |
| 공공데이터포털 금융위원회 주식시세정보 | 공공누리라 라이선스는 깨끗하나 비수정주가일 가능성이 크고 보유 기간·상폐·구성 정보 유무 미확인. 보조 |

KRX 를 수작업으로 받는 안은 메뉴가 종목별·날짜별이라 200종목 10년치에 비현실적이라 뺐다.
사용자가 "내가 받아서 넘기면 되지 않느냐"고 했고 그 뜻은 맞지만, 받는 주체는 스크립트다.

### 4. LLM — 간결함이 무료 API 보다 낫다

공고 원문은 "출품작 제작 시 ChatKHU 필수 사용, 외부 AI 병행 가능(사유 기재)"이다. 앱이
실행 중에 ChatKHU 를 호출해야 한다는 조항은 없지만, AI 활용도 30점이 "ChatKHU 등 AI 활용의
깊이"이고 1단계 설계와 README 가 이미 ChatKHU 를 LLM 자리에 적었다.

AI 가 제안한 "개발은 Gemini 무료 API, 시연은 ChatKHU" 는 사용자가 기각했다. 이유는 간결함이다
— 서식4 에 외부 AI 를 하나 더 적어야 하고, 모델이 다르면 구조화 품질을 ChatKHU 모델로 다시
검증해야 한다. ChatKHU 크레딧은 기본 4,000 에 요청하면 30,000 을 더 받을 수 있어, 개발에서
ChatKHU 를 안 쓰면 거의 전부 호출 테스트·시연에 남는다.

### 5. DB — 파일 하나, 테이블로 나눈다

파일을 나눌 이유가 없다. 테이블 네 개 초안은 `docs/workflow/2_자료준비단계.md` §1 에 있고
사용자가 한 번 더 검토한다. DB 이름의 상징성(전 프로젝트의 `prodex.db` 처럼)은 기능과 무관하다.
